# Project Management SaaS

A multi-tenant project management platform: **React + TypeScript** frontend, **ASP.NET Core (.NET 9)** API, **PostgreSQL** (SQLite for local development). It implements the MVP from the product spec plus a good part of Phase 2, using the lavender-glass UI from the reference app (light theme, and the charcoal + lavender dark theme).

## Quick start (no database server needed)

Requirements: .NET 9 SDK, Node 20+.

```powershell
# 1. API  (http://localhost:5080, Swagger at /swagger) — uses a local SQLite file in Development
dotnet run --project backend/src/ProjectManagement.Api --launch-profile http

# 2. Web  (http://localhost:5173) — proxies /api to the API
cd frontend
npm install
npm run dev
```

In Development the API creates the database, seeds the plans, a platform admin and demo data:

| Account | Password | What it is |
|---|---|---|
| `demo@example.com` | `Demo@12345` | Owner of **Qruize Technologies** (Pro plan, 4 projects, teams, tasks) and a personal Free workspace |
| `arun@`, `priya@`, `kumar@`, `sridhar@`, `umar@example.com` | `Demo@12345` | Admin / Manager / Member / Member / **Guest** in that organization |
| `admin@example.com` | `Admin@12345` | Platform administrator — gets an admin-only interface (Overview, Organizations, Users, Plans, Audit logs); no projects, tasks or reports |

There is no email server in development: verification, password-reset and invitation links show up in the **dev mailbox** at `http://localhost:5173/dev/mailbox`.

> **Upgrading a local SQLite dev database:** SQLite databases are created with `EnsureCreated` and are not migrated. If you have a `pm-dev.db` from an earlier version, delete it and let the API recreate it (PostgreSQL applies migrations automatically).

### Tests

```powershell
cd backend; dotnet test          # integration tests against the real API (SQLite)
cd frontend; npm run build   # type-checks and builds the frontend
```

### Docker / PostgreSQL

```powershell
copy .env.example .env      # set POSTGRES_PASSWORD and JWT_SIGNING_KEY; uncomment the SEED_* lines for demo data
docker compose up --build   # http://localhost:8080  (PostgreSQL + API + nginx; ports bound to localhost)
docker compose logs api     # in this mode verification / reset / invitation links are printed here
docker compose down         # stop (add -v to also delete the database volume)
```

This local stack also runs a **nightly backup** service. To put the app on a real server with HTTPS, e-mail and backups, follow **[deploy/DEPLOY.md](deploy/DEPLOY.md)**.

To run the API from your IDE against PostgreSQL instead of SQLite: `docker compose up -d db`, then set `Database__Provider=Postgres` and the connection string. The initial EF migration is in `backend/src/ProjectManagement.Infrastructure/Persistence/Migrations`; it is applied automatically on startup (`Database:AutoMigrate`).

## What is implemented

| Area | Status |
|---|---|
| **Auth** | Register, email verification, login, JWT access token (15 min) + rotating refresh token in an HttpOnly cookie, reuse detection, logout / logout-all, password reset & change, account lockout, session list & revoke, rate limiting |
| **Password policy** | One policy for the whole platform (Admin → Platform settings → Password policy): minimum length (8–64), which character kinds are required (letter, uppercase, lowercase, digit, symbol), whether common passwords are refused (checked against a list plus the usual disguises — `P@ssw0rd`, `Welcome2026`, leetspeak), whether a password containing the person's name or email is refused, and how many recent passwords (0–10, including the current one) cannot be reused. Enforced on sign-up, reset and change; changing the policy applies to passwords chosen from then on and never locks out someone with an older password. The sign-up, reset and change-password forms show a live checklist that ticks off each rule as it's typed; the server has the final say (common/personal/reuse checks aren't done in the browser). `GET /api/v1/auth/password-policy` is public so a form can read the current rules. |
| **Workspaces** | Personal + Organization workspaces on the same model, workspace switcher, invitations (email-bound, expiring), member roles (Owner/Admin/Manager/Member/Guest), per-tenant permission overrides |
| **Organization chart** | Dedicated **Organization** page (Chart + Roles tabs). Job roles form a tree (e.g. CTO → Principal Manager → …); connect roles on a canvas by dragging from one role's bottom dot to another's top dot (remap = connect elsewhere, disconnect = click the line), add / edit roles, **soft-delete / restore** them (people and sub-roles are moved to a chosen role first). Drag people from the "No role yet" tray onto roles; a **People** view draws who reports to whom. Loops are rejected server-side, positions are saved, changes are audited, and connect / move actions have an Undo toast. Starter template for a software company. Everyone except guests can view; only holders of `org.structure` (Owner / Admin by default) can edit. |
| **Job-role access** | Organization page → **Access** tab. For every job role an admin sets a level per menu (**None / View / Edit / Full**; Projects, Tasks, Calendar, Teams, Members, Organization, Reports, Activity, Audit log, Billing) plus extra switches (comment, delete, labels, workflows, invite, manage members, edit the chart, manage access). Menus disappear for **None**, create / edit buttons disappear for **View**, and the API refuses the same calls (`MODULE_ACCESS_DENIED` / `PERMISSION_DENIED`), including on the dashboard and in search. Owners and Admins are never narrowed by a job role; a role with no settings of its own keeps the defaults of the person's access level. **Delegation:** only Owners / Admins can hand out "manage job-role access" (and the invite / manage-members / edit-chart switches); a delegate can only change roles *below* theirs in the chart and never grant more than they have. "All roles at a glance" matrix, "Use suggested" starting points for the template roles, copy-from another role, reset to defaults, every change audited. Editing needs the Business plan (existing profiles keep applying after a downgrade) |
| **Multi-tenancy** | `TenantId` on every tenant-owned row, EF global query filters (default-deny), write guard in `SaveChanges`, tenant/role resolved server-side from the token + database on every request |
| **Projects** | CRUD, project members, health (on track / at risk / delayed), archive, soft delete, optimistic concurrency. The **Projects page** shows **every project of the organization to Owners, Admins and Managers** (an **All projects / My projects** switch narrows it to the ones they belong to), and only the projects they belong to (`ProjectMember`) to Members and Guests (Guests are also limited to those everywhere else); a direct link (search, a notification, a task's project) still opens a project a Member isn't listed on, this only narrows what's *listed* (`GET /projects?mineOnly=true`) |
| **Views** | Projects page: **Cards / List / Board** switcher (Board = projects by status; dropping in another column changes status, dropping within a column only re-orders, order is persisted). Inside a project: Kanban (drag & drop), List, **horizontal data-driven Timeline** pinned at the top of the project page under the summary (editable stages, delayed state, tasks done per stage); the **Workflow** tab shows the statuses as connected steps you drag into a new order (or reorder with Alt + arrows, or the arrow buttons on touch screens) — one call saves the whole order and the board columns follow it (`PUT /projects/{id}/statuses/order`) |
| **Searchable dropdowns** | Every dropdown in the app (filters, forms, dialogs, tables) has a **search box**: opening it focuses the search, typing narrows the options and highlights the match, the arrow keys move, **Enter** chooses, **Esc** closes only the list (not the dialog it is in), and typing on a focused field opens it already searching. It is one component (`frontend/src/components/Select.tsx`) that takes the same props and `<option>` children as a native `<select>`, so new dropdowns just use `<Select className="select" …>`; the list opens above dialogs and flips upwards near the bottom of the window |
| **Tasks** | CRUD, assignee, priority, per-project configurable statuses, labels, subtasks, comments with @mentions, file attachments, activity feed, notifications. **Editing is assignee-scoped for regular Members**: a Member sees every task in a project they belong to, but can change one (status, fields, checklist, time, attachments, dependencies, subtasks) only when it's assigned to them — everyone else's tasks are read-only, enforced server-side (`403 PERMISSION_DENIED`) on every task-editing endpoint, not just the UI. Owners, Admins and Managers keep the same full edit rights as before, on any task |
| **Milestones & dependencies** | Milestones per project (own tab): name, dates, owner, status, and **progress worked out from the tasks that count towards them**, with overdue detection; they also appear on the calendar. Tasks depend on other tasks with all four link types (**finish→start, start→start, finish→finish, start→finish**), managed in the task modal. Links are validated on the server: no self-links, duplicates, **loops** or links across projects. Projects can **enforce** dependencies: a task then cannot start or finish before the tasks it depends on (the API answers `409 DEPENDENCY_BLOCKED` with the reason, the board card shows a lock), while going back, blocking or cancelling is always allowed and a cancelled predecessor stops holding the plan up. The switch is in the project's Edit dialog |
| **Create users directly** | Besides inviting by email, an organization **Owner or Admin** (the *members.manage* permission) can create a person's account on **Members → Create user**: name, email, role, optional job role / reports-to, and a temporary password (generated by default, checked against the platform password policy). The person can sign in straight away (their email counts as verified, and they land in the organization) but the server refuses everything except signing in/out, `GET /me` and changing the password (`403 PASSWORD_CHANGE_REQUIRED`) until they replace it, and the app shows a "Choose your password" screen in place of the workspace; the temporary password cannot be reused. The password is shown to the administrator once (with a copy button), is never emailed, logged or audited (the person gets a notice email without it, and the audit trail records `member.created`). An address that already has an account is refused (`409 ACCOUNT_EXISTS`) with a pointer to invite them instead, so nobody's account or password is ever overwritten; a pending invitation for the same address is revoked; roles above or equal to the creator's own cannot be given; counts against the plan's member limit; not available in personal workspaces. Endpoint: `POST /api/v1/workspace/members`. Admin-created accounts get no personal workspace |
| **Invitations with a job role** | When inviting, people with the org-structure permission can also pick the person's **job role** and **who they report to**. On acceptance they land on the organization chart in that role, so the role's access settings (menus, view/edit levels) apply from their first sign-in. The invitation email, pending-invitations table, accept page and Members list all show the job role. If the role was deleted or the manager left in the meantime, the person simply starts unplaced |
| **Files** | Attachments on projects (Files tab) and on tasks (task modal): drag-and-drop or picker, image thumbnails, download, delete. Storage is abstracted (`IFileStorage`): local disk for development, or any **S3-compatible bucket** (AWS S3, Cloudflare R2, Backblaze B2, MinIO ...) for production, so every API server sees the same files and nothing is lost when a server is replaced; switching to a bucket copies the files already on local disk into it at start-up. The bytes never go into PostgreSQL, and downloads still stream through the API, where the permission checks are. Server-side rules: allow-list of extensions **and** a matching content check (an `.exe` renamed to `.png` is refused), name sanitising (storage keys are server-generated, never the file name), per-plan **file-size** and **total storage** limits, `nosniff` + sandboxed download headers, and the same project/task permissions as everything else. Files of deleted projects stop counting against storage immediately and are erased a week later by the maintenance worker. Global search finds files by name |
| **Teams, Reports, Dashboard, Search, Calendar** | Yes (reports: completion, per-day chart, status split, project progress, workload, CSV export). **Date filters** (Date / Range / Dates) on the Calendar and Timesheet pages light up a day as soon as the pointer or keyboard focus is on it, preview the whole range up to the hovered day while a range is being chosen, and light up the picked date / range as a whole when it is hovered. The Calendar page has no "Add Task" button: tasks are created from the Dashboard or inside a project |
| **Chat** | Live chat inside an organization workspace (Chat in the menu; not in personal workspaces, not for guests). **Direct messages** between two people (one chat per pair, whoever starts it) and **groups** (2–50 people; the creator is an admin who can rename, add and remove people; anyone can leave, and a group always keeps an admin). Messages arrive instantly over a WebSocket (SignalR at `/hubs/chat`, falling back to long polling): new messages, edits and deletes, **typing** indicators, **who is online**, and **read receipts** — a grey single tick once a message is sent, turning into a coloured double tick once everyone else in the conversation has read it (the other person in a direct chat, everyone in a group) — with an unread count in the menu, in the list and per conversation. Messages support **bold**, *italic* and __underline__ (toolbar buttons or Ctrl+B/I/U, written as `**bold**`, `*italic*`, `__underline__`) and an **emoji picker**; formatting marks never leak into previews, search results or reply quotes, which stay plain text. **Reply** to a message (quoted), **edit** and **delete** your own (a group admin can delete anyone's; deleted text is erased, not hidden), links are clickable, **search** across your own conversations, **mute** a conversation (no pop-up, no menu count), drafts are kept per conversation, and a browser pop-up or in-app toast appears for messages that arrive while you are elsewhere. People added to a group see messages from then on, not earlier ones. The server checks every action (membership, role, workspace): a conversation you are not in answers "not found", another workspace's people cannot be reached, and someone removed from the workspace stops receiving at once. Sending goes through the normal API (validated, 4,000 characters); the socket only carries news out and "typing" in, and it is closed when the access token runs out so the browser reconnects with a fresh one. Not built: file attachments, emoji reactions, @mentions, message retention limits. With Redis configured, chat runs on **several API servers**: SignalR uses the Redis backplane (an event published on one server reaches the clients of all of them) and online status is counted in Redis, with each server confirming its own connections every 30 seconds so a crashed server's people go offline within 90 seconds. Without Redis it all stays in memory, for one server |
| **Notifications** | Bell + notifications page, **e-mail** and **desktop (browser) notifications**. Settings → Notifications lets each person choose, per event (task assigned, mention, comment, due soon, overdue, invitation, billing, security), whether it arrives in the app, by e-mail, and/or as a desktop pop-up; **security alerts cannot be switched off**. E-mails are queued and sent by a background worker with retries (a slow or broken mail server never delays a request), and a "Send test email" button reports whether delivery works. Password changes / resets raise a security alert. Desktop notifications need the browser permission and work while the app is open in a tab (there is no service-worker push yet) |
| **Two-step verification (MFA)** | Settings → Security: authenticator-app codes (TOTP, RFC 6238 - works with Microsoft/Google Authenticator, 1Password, Authy) set up by QR code, 10 one-time **recovery codes**, sign-in becomes password → code. Secrets are AES-GCM encrypted at rest (`Mfa:EncryptionKey`, or derived from the JWT key), codes cannot be replayed, wrong codes count toward the same account lockout, turning it off or regenerating codes needs the password **and** a code, and a platform admin can reset it for someone who lost their device (audited, signs them out). Every change raises a security alert |
| **Organization security** | Organization → Security (owners and admins; Business plan and above, `ADVANCED_SECURITY` feature): **require two-step verification** for everyone in the workspace, and/or **restrict by network address** (one IP or CIDR range per line). Enforced server-side on every request that resolves a workspace, not just at sign-in. Turning either rule on is blocked while it would lock the person saving it out (their own two-step verification must already be on to require it; their own current address must already be in the list to enable the allowlist) — the Security tab shows the reason and an "Add it" button fills in the admin's own address. A member who is cut off is not hard-failed: `/me` reports which workspace refused them and why (`ORG_MFA_REQUIRED` / `ORG_IP_BLOCKED`), and the app shows an in-place recovery screen — turn on two-step verification right there (still showing the one-time recovery codes before returning) or switch to another workspace — instead of a dead end. If the plan's advanced-security entitlement lapses, the settings are kept but stop being enforced (fail-open) rather than locking everyone out |
| **Consent management** | Terms of Service / Privacy Policy acceptance is tracked per person, not just clicked away. Sign-up requires ticking "I agree to the Terms of Service and Privacy Policy" (a viewable link, enforced server-side too); Admin → Platform settings → Legal documents lets a platform administrator write and **publish** each document, which bumps its version. Publishing asks everyone who already accepted an older version to accept again — reading and signing in keep working, but changing anything is paused (`403 CONSENT_REQUIRED`) until they do, with a full-screen in-app prompt (`GET /me`'s `pendingConsent`) that shows the new text and a one-click **I accept**, no reload or re-login needed. Nobody is retroactively blocked by documents nobody ever published: an unpublished document (version 0) never counts as pending, so existing and seeded accounts are unaffected until an admin actually publishes real text. Settings → Security also lists the documents you've accepted for reference |
| **API keys** | Settings → API keys (owners and admins; Business plan and above): secrets like `pmk_ab12cd34_...` for scripts and integrations, sent as `Authorization: Bearer <key>` or `X-Api-Key`. A key acts as the person who created it, in one workspace, with that person's *current* role (demote or remove them and the key follows), and is either read-only or read & write, optionally expiring in 30 / 90 / 365 days. The secret is shown once and only its SHA-256 hash is stored; keys are revoked individually, show last-used time and address, are rate-limited separately from the person's browser use, and creation / revocation is audited. No key can ever reach key management, billing, account / password / MFA, administration or workspace switching. Max 20 active keys per workspace |
| **Go-live tooling** | See **[deploy/DEPLOY.md](deploy/DEPLOY.md)**. A production overlay (`deploy/docker-compose.prod.yml`) puts **Caddy** in front for automatic HTTPS certificates and publishes only ports 80 / 443 (database and web container unreachable from outside); a bundled **backup service** dumps the database and uploaded files every night (kept 14 days) and `deploy/restore.sh` restores them (with a `--verify-only` mode that proves a backup is readable without touching live data, and a safety copy of the replaced database) - both were exercised end to end on the Docker stack. In the admin portal, **System health → Go-live checklist** inspects the running configuration (never showing a secret): default administrator / demo passwords, e-mail provider, HTTPS, CORS, key strength, rate limiting, webhook safety, database password and **backup freshness**, worst first with the fix for each, plus **Send test email to me**; the admin Overview shows a red notice until nothing needs fixing |
| **Platform administration (more)** | For platform administrators, in the admin portal: **Billing** - monthly / annual recurring revenue, paying organizations, trials (and those ending within 7 days), past-due, 30-day collections and failed payments, revenue by plan, recent invoices. **Usage** - per organization members, projects, tasks, storage, active API keys / webhooks and last activity, sortable and searchable, with warnings when an organization is at 80 %+ of a plan limit (counts only - customer content is never shown). **Plan exceptions** - give one organization more (or less) of a feature or limit for a set time or for good ("API access for 30 days while they evaluate"), with a mandatory reason and audit entry; it flows through the same entitlement checks and live-updates their menus. **Platform settings** - close sign-ups (invited people can still join), **maintenance mode** (changes paused for everyone except platform administrators; reading and sign-in still work; HTTP 503 `MAINTENANCE_MODE`) and an **announcement banner** shown on every page including the sign-in page. **System health** - database reachability / latency / pending schema updates, each background worker's last round (ok / stalled / error), queue depths (e-mails, report exports, webhook deliveries), request and server-error counters since start, uploaded-file storage and an overall Healthy / Degraded / Down verdict |
| **Reporting-line visibility** | **My team** (menu item appears for anyone with people below them in the organization chart): everyone who reports to me, directly or through others (each card tagged Direct or Indirect report, all aligned on the same left edge), with open / overdue task counts, tasks finished in the last 30 days, time logged in the last 7 days and their next five most urgent tasks; "All n open tasks" opens the full list for one person. It is **read-only** and does not depend on project membership or the reports permission - managing people means seeing their work. Managers can also open the **timesheet** of anyone in their line (the Timesheet page lists them). Only downward: peers, bosses and other workspaces are never visible, loops cannot form in the chart, and moving someone in the chart changes what their old and new managers see immediately |
| **Live access updates** | Menus, buttons and pages follow changes to a person's role, permissions, job-role access or plan **without a page reload**: the app compares a short server-computed fingerprint of the person's access (`GET /me/fingerprint`, also included in `GET /me`) every 30 s and whenever the tab regains focus, and reloads the context and cached data when it differs, with an "Your access was updated" notice. Server-side enforcement never depended on this - it always reads the current role from the database - so the delay only affects what is shown |
| **Webhooks** | Settings → Webhooks (owners and admins; Business plan and above): up to 10 addresses that receive a signed `POST` for chosen events (`task.created`, `task.status_changed`, `sprint.started`, ... or groups such as `task.*`, or everything). Body: `{ id, event, occurredAt, workspaceId, data: { summary, entity, projectId, actor, oldValue, newValue } }`. Headers: `X-PM-Event`, `X-PM-Delivery`, `X-PM-Timestamp` and `X-PM-Signature: t=<unix>,v1=<hex HMAC-SHA256 of "<t>.<body>" with the secret>` (secret shown once, can be rotated). Delivery is done by a background worker from the activity feed: at-least-once, retried after 1 min / 5 min / 30 min / 2 h / 12 h (6 attempts), failed deliveries can be retried by hand, a receiver whose deliveries fail 10 times in a row is switched off automatically, history is kept 14 days, and only events after the webhook was created (or turned back on) are sent. **Safety:** addresses must be `https://`, are resolved and checked when saved *and* at connection time, and anything pointing at loopback, private, link-local (cloud metadata) or carrier-grade-NAT ranges is refused; redirects are not followed; 10 s timeout. `Webhooks:AllowPrivateTargets` (compose: `WEBHOOKS_ALLOW_PRIVATE`) lifts this for development only. API keys cannot manage webhooks |
| **Custom fields** | Settings → Custom fields: up to 20 workspace-wide extra fields on every task - text, number, date, dropdown (up to 30 choices) or checkbox - with names, ordering and a used-on-N-tasks count. Values appear in the task dialog (saved as you change them; also fillable while creating a task), are validated per type and stored in a canonical form, changes are logged in the activity feed, and each field becomes a column in task exports and can be mapped in CSV import (a header that matches a field name is mapped automatically). The type of a field is fixed once created; deleting a field deletes its values (after a confirmation that says how many). Needs the Pro plan and the manage-workflow permission to define fields; anyone who can edit a task can fill them. Not yet: filtering or sorting task lists by a custom field, and per-project fields |
| **CSV import** | Project → Import: choose a CSV (comma, semicolon or tab separated, UTF-8, quotes and line breaks inside cells supported; up to 5,000 rows / 2 MB), match its columns to Title, Description, Status, Priority, Assignee, Start / Due date, Estimated hours, Labels and Milestone (columns are guessed from the header names), and see how many rows are ready and exactly which rows have which problem *before* anything is written. Dates are read day-first or month-first as chosen; priorities accept your custom names; assignees match by e-mail or full name; unknown statuses / people / milestones are reported per row. All-or-nothing by default, or skip the bad rows and import the rest; missing labels can be created (max 20 at once). Plan task limits and archived projects are respected; the import writes one activity entry and an audit record, and does not send assignment notifications or run automation rules. A template file can be downloaded from the dialog |
| **Dark mode** | The top-bar moon / sun button (or Settings → Appearance) switches the theme; the choice is remembered on the device. Dark is a deep slate-blue palette rather than black: the sidebar and top bar are the darkest layer, the page a step lighter, cards and panels lighter again, and menus, drawers and dialogs lighter still, so depth (soft borders, small shadows) separates areas instead of one flat colour. The violet accent is kept for the active menu item, primary buttons, the selected project, progress and links; hovers, borders, scrollbars, avatars and tabs are neutral, status colours (success, warning, delayed / blocked, completed) are softened but stay distinct, charts are eased down so nothing looks neon, and every text colour passes 4.5:1 contrast on the surfaces it appears on. Switching cross-fades the whole page (a plain colour fade where the browser lacks view transitions, and no animation if reduced motion is requested). The palette is in styles/tokens.css and the component skin in styles/dark.css |
| **Project types** | Every project has a **Project type** that says what it is for: *New Project*, *Change Request (CR)*, *Enhancement*, *Migration*, *Integration*, *Upgrade*, *Maintenance*, *Compliance / Regulatory* or *Other*. It is **required when a project is created** (the dialog and the API answer *Choose a project type* otherwise, `projectType` on `POST /projects`), can be changed later in the Edit dialog (an update that leaves it out keeps it), and is shown wherever the project is presented: the project cards and list (with a **Type** column and an *All types* filter, `?projectType=`), the project page and the Project Status page header. Projects that existed before types were introduced are *Other* |
| **Work management** | **Work tasks** are operational activities that are *not* project tasks - bug fixes, issue and technical analysis, data preparation and correction, production support, report preparation, performance analysis, configuration changes, deployment support, customer requests, maintenance, ad-hoc work - kept apart from a project's timeline, stages and dependencies (own tables, API `api/v1/work-tasks`, own permissions and pages). The **Work management** menu has **All work tasks**, **My work** and **Work reports**. A work task has a title, description, **work type**, an optional **related project** (any project you can see, completed and archived ones too - it is used for reference, reporting and traceability only and **never changes the project: a completed project stays completed**, and the work never appears among the project's tasks or history; the project page has a *Work tasks* link that opens the list filtered to it), an assignee (not guests; they are notified), priority, start and due date, a status of its own (*To Do, In Progress, On Hold, Completed, Cancelled*), its own **comments**, **files** and **history**. A work task needs no project at all. The list searches (title, description, `WT-12`), filters by work type, related project (or *no related project*), assignee, priority, status, open / closed, due range and overdue, sorts by any column, pages, and exports the filtered list as CSV (`GET /work-tasks/export`; cells that start with `=`, `+`, `-` or `@` are neutralised). **Work reports** shows open, overdue, due-this-week, unassigned, raised and completed counts for a chosen period, a daily trend, and breakdowns by work type, status, person and related project (`GET /work-tasks/summary`); the dashboard has *My work tasks* and *Open work tasks* cards. **Work types** are the workspace's own list (Settings → Work types; the standard 14 are created the first time): add, rename, describe, reorder, switch off; one that work tasks use cannot be deleted, only switched off (it stays on those tasks). Access: a **Work management** module in the job-role access matrix (guests never see it); members can create work tasks and change the ones assigned to them or raised by them, managers can change and delete any, and only admins manage work types (`work.create`, `work.edit`, `work.delete`, `work.types.manage`) |
| **Project groups** | Every project belongs to **one project group** from the workspace's own master list (Salesforce Projects, Employee Portal, Data Team, Payment Engine, HRMS, Mobile Applications, Other Projects ... whatever you define). **Project group is a required field** when a project is created (the dialog and the API answer *Choose a project group* otherwise) and can be changed later from the project's Edit dialog; the Projects page shows the group on each card and can filter by it. A new workspace starts with one group, **Other Projects**, and projects that predate groups were put in it. **Project groups** (Workspace menu, for people with the *Manage project groups* permission - Owners and Admins by default, and job roles with Projects at Full access) lists the groups with how many projects each holds: **add, rename, describe, reorder (drag or arrows), activate / deactivate and delete**. An inactive group is no longer offered for new projects but keeps the ones it has (they still show it). A group that still holds projects (archived ones included) is deleted only by **moving them to another active group first** (`409 PROJECT_GROUP_IN_USE` otherwise); names are unique, and at least one group stays active. Everyone who can see projects can read the list |
| **Delivery date history** | Every change of a **due date** of a project, task or sub-task is kept: the date before and after, who changed it, when (to the minute), the **reason** and what it **depended on**. Moving a date **later** (or clearing it) needs a reason (`dueDateReason`, `422` otherwise; *Dependency causing it* is optional); bringing a date forward needs none. The task and project edit dialogs ask for it as soon as an existing due date is changed. | **Installable app & push** | A web app manifest and service worker: install from the browser, start offline on the last saved My work (cleared on sign-out; API data is never cached), and **push notifications** to devices (Web Push with VAPID keys made on first use, payloads encrypted per RFC 8291) for the events ticked in the Desktop column - My notifications → Push on this device. `Push:WorkerEnabled`, `Push:IntervalSeconds`, `Push:Subject` |
| **Redis** | Optional (`REDIS_URL`, `--profile redis`): a shared cache of each workspace's plan/entitlements (30 s, `Cache__EntitlementSeconds`, 0 = off; subscription and exception changes invalidate at once, plan-definition edits reach other servers within the TTL) rate-limit counters shared by all API servers, the SignalR backplane and online status for chat. Without it, in-process memory (one API server). A down Redis only slows things; Admin → System health shows the cache. |

### Not built yet (from the spec's later phases)

Azure Blob / GCS storage (local disk and any S3-compatible bucket are built in), virus scanning of uploads, i18n. The design leaves room for them (entitlement keys, provider abstractions for email/payments, tenant-aware model), but none are wired up.

## Architecture

```
backend/                            the API (.NET 9): ProjectManagement.sln, Directory.Build.props, Dockerfile, src/
  src/
    ProjectManagement.Domain          entities, enums, permission & feature catalogs (no dependencies)
    ProjectManagement.Application     services (auth, workspaces, projects, tasks, billing, ...), DTOs, validators
    ProjectManagement.Infrastructure  EF Core DbContext + migrations, JWT, password hashing, email/payment providers, worker
    ProjectManagement.Api             controllers, middleware (exceptions, request context, security headers), filters
    ProjectManagement.Tests           integration tests (WebApplicationFactory)
frontend/                           React 19 + Vite + TanStack Query + Zustand + React Hook Form/Zod, feature folders
```

Request pipeline: exception handler → security headers → CORS → JWT → rate limiter → **request context** (validates the session, user, workspace membership and role against the database) → controllers → FluentValidation → service (permission check → entitlement check → business rule) → activity/audit written in the same transaction.

Design decisions worth knowing:

- **The client never supplies a tenant.** The workspace id lives in the signed access token and is only issued by `POST /workspaces/{id}/switch` after a membership check. Removed members, revoked sessions and disabled users lose access immediately (checked per request, not just at token expiry).
- **Refresh token in an HttpOnly, SameSite=Strict cookie**; the access token is kept in memory only. Cookie refresh additionally requires an `X-Requested-With` header (CSRF defence). API clients can send `X-Token-Delivery: body` to receive the refresh token in the response body.
- **Every page lives under its organization:** `https://host/{organization-address}/projects/{id}`, `/{organization-address}/ai`, and so on. The address is made from the organization's name when it is created (`Acme Bank` → `acme-bank`; a name that equals one of the app's own paths, such as `Projects` or `API`, becomes `projects-org`; the list is `WorkspaceSlugs.Reserved` on the server and `RESERVED_SEGMENTS` in `frontend/src/lib/orgPath.ts`). The router's base path is taken from the address, so every link inside the app is unchanged and still lands in the right place. Opening a link into another of your organizations switches to it first (the tab title shows its name); an older link without an organization (`/projects/42`, from an old e-mail) is sent to the same page in your current one; signed out, a deep link goes to sign-in and comes back to the same page. E-mail, push and Slack/Teams links carry the address too. There is no user segment: the signed-in person is implicit, and a link has to work for a colleague as well.
- **Usage is computed live** from row counts (projects, tasks, members + pending invites, teams) rather than stored counters, so it cannot drift.
- **Enums are stored as strings** and dates as `DateOnly` / UTC `DateTime`, so the same model runs on PostgreSQL and SQLite.
- Responses use the spec's envelope (`success / data / message / errors / traceId`); validation failures are `422` with per-field errors, plan limits are `403 PLAN_LIMIT_REACHED`, stale edits are `409 VERSION_CONFLICT`.
